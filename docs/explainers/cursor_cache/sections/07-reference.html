Open questions and glossary

What the investigation did not settle, with the confidence each reading carries, and the terms the page uses.

Open questions

  1. Why is a 64-byte stride slow at the frontier? Ruled out: 4K aliasing, more line sharing, codegen. Padding to 72 bytes fixes it. No counter run has looked at it: the kperf counters of section 6 measured the one-record hand-off only.
  2. Why did #41 slow two single-thread benchmarks? Settled. The M4's whole-lap fill_drain followed the drain loop head's address mod 8 and measured equal within 0.5% with loop heads pinned; whether verb/bench should pin them is #53. The x86 runner's 22% loss on one-record drains was the compiled shape of the first version (a length LLVM could not see as constant); the final version measures +17…+21% on a Zen 3 runner (#50).
  3. What holds TypedSlot at 16384 slots to 25–48 M/s? Answered: past a slot-array size the producer's stores stall and the consumer gets stuck polling one record behind. The onset follows slot size (none to 65536 for 8-byte slots, from 16384 for 16-byte, from 2048 for 32-byte), the cache moves it from 16384 to 8192, and a producer store prefetch removes it (#49, #54). Why the stores stall, an L1 miss or a coherence upgrade, no counter run has checked.
  4. Why is the two-thread one-record hand-off slower with #41 on a Zen 3 core? Bounded (#55, section 6). It is a lean-consumer regime. At no consumer work #41 measured −38…−41% and −32…−36% against master on two Zen 3 VMs; the loss shrinks with every step of the consumer-work knob, crosses zero at about four and is a gain at eight. Pinned to SMT siblings and on Zen 5, #41 gains at every step. 128-byte padding flips no row, which rules out the prefetcher-pairing hypothesis. Still open: why a lean consumer deepens the lockstep on Zen 3, and the 16384-slot cell (−74% in Bench Compare), which was not swept. This remains the open merge question for #41.
  5. Why are rtrb's misses cheap with a near-empty consumer? Open. On the M4 at 64 slots, rtrb and ring take about the same number of L1D load misses per record (0.69 against 0.78 in the consumer), and ring's cost 4–6x more cycles. Slot size, consumer shape, producer shape, cursor order, code and placement were tested one at a time and none closed the gap; rtrb's 64-slot lead exists only at zero consumer work (section 6). The counters cannot say which line misses.
  6. Which mode of the bimodal popN 1024 cell is typical? The regimes review attributes the two modes to the chase's initial race (high confidence). A separate review tied the tagged flip to the slot array sitting one page after the ring, mechanism unknown.
  7. Where does the lockstep threshold sit now? The cache moved it. The steady-state model R* ≈ m / (c − p) (m one refresh ≈ 45 ns, c the consumer's cost per pop, p the producer's cost per push) was fitted qualitatively; c and p were never measured in isolation.
  8. Does the one-line layout batch about 4 records per transfer? Consistent with the timings (one-way 37.8 ns against ~9–10 ns per record). The kperf counters read since count misses per record but cannot say which line missed, so it is still unobserved. Hypothesis, ~70% confidence.
  9. Should CACHE_LINE become 128? Tested, not decided. On the M4 with #41, 128-byte padding equals the two-line layout at 64 slots (109 against 111 M/s) and gives the steadiest 1024-slot result (395, all five rounds 375–398); single-thread cells do not move (within 1–3%). For master it helps only against the unlucky layout (42 against 31) and loses to the lucky one (98). On Zen 3 it moves neither side by more than ~10%; on Zen 5 it lifts master by up to 24% at no consumer work, and #41 still leads (section 5, #55).
  10. Should the producer keep the capacity in a field? Tested and dropped. On the shipped path it helps the two-line layout by 0 to +15%, and costs CopySlot's single-thread push_pop 16% (2.56 → 2.98 ns), its whole-lap drain 10% (1280 → 1150 M/s) and TypedSlot's one-line 64-slot hand-off about 15%. No PR (section 6).

Glossary

Cache line
The unit a cache stores, moves and keeps coherent. 128 bytes on this M4 Pro, 64 on the x86 CI runners; ring_align assumes 64.
Coherence transfer
Moving a line, or its write ownership, from one core's cache to another's, invalidating the old copy. One way inside a P-core cluster: median 37.8 ns.
Stride
Bytes from the start of one slot to the start of the next: 16 for TypedSlot<u64>, 8 for CopySlot<u64>, 72 against 64 and 264 against 256 for the wide records.
Frontier
The slots the producer is writing while the consumer reads right behind it. Lines there are hot on both cores at once.
Lockstep
The full ring with the producer one slot behind the consumer: it refreshes its cached consumer cursor before nearly every push, about 48 ns each.
OWN, GATING, HANDOFF
The three orderings the ring uses. OWN is Relaxed: an end reading the cursor only it writes. GATING is Acquire: reading the other end's cursor before touching the slots it guards. HANDOFF is Release: publishing one's own cursor after the slot writes.
LDAPR, STLR
The AArch64 instructions behind them: LDAPR (and LDAPUR) an acquire load in the weaker RCpc form, STLR (and STLUR) a release store. A push does one STLR; before #41, every pop did one LDAPR.
rtrb
The rtrb 0.4 crate, a published single-producer, single-consumer ring with 8-byte slots for a u64. Section 6 compares ring against it.
Rung
One step of section 6's comparison: ring with one more difference from rtrb removed, measured beside rtrb in the same run.
Consumer work
A benchmark knob that makes the consumer run n dependent multiply-adds per record, the same for every candidate.
Lean-consumer regime
A consumer that does almost no work per record. On the M4, rtrb's 64-slot lead over ring exists only there; on Zen 3, #41's loss against master lives there and turns into a gain by eight steps of consumer work (#55).
Refused push
A push the ring turns away because it is full. Counted per record, as in #55's 1.2 for #41 against 0.7 for master at no consumer work.
kperf
macOS's interface to the CPU's performance counters. Section 6 reads cycles, instructions and L1D misses per thread through it.
Placement harness
#51: the bench harness builds each ring at a chosen byte of a 256-byte block (0 or 64), so a run reports one cursor layout instead of whatever the stack gave it.
Bench Compare
The CI job that runs a PR's base and head in the same run and reports the change per benchmark.
SMT siblings
The two hardware threads of one physical core. A pair pinned there shares that core's L1 cache.
loom
A Rust model checker. It runs a concurrent test under every interleaving the memory model permits, up to a bound, and so catches orderings a real run rarely exposes.
