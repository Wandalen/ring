Cache lines

A core never fetches one byte from memory. It fetches a cache line: a fixed, aligned block of bytes that the caches store, copy and track as one unit. Touch one byte and the whole line comes along. The line is 64 bytes on x86 and most ARM cores. It is 128 bytes on Apple silicon, including the Apple M4 Pro where every number in this explainer was measured.

The unit the memory system moves

The ruler below is 256 bytes of memory, split into 8-byte words (one u64 each). Switch the line size and pick a word: the highlighted span is everything that moves with it.

Line size

One line, two cores

Each core keeps its own copy of a line in its L1 cache. A coherence protocol keeps the copies consistent with two rules. To write, a core must hold the only valid copy; every other copy is invalidated first. To read, a core needs a valid copy; several cores may hold the same line read-only, shared. When the up-to-date copy lives in the other core, the line has to cross over. On this machine one crossing between two performance cores in the same cluster took a median 37.8 ns (p25 37.3, p75 38.2). Across clusters it took 58 to 105 ns.

The simulator runs core A and core B in turns. A writes word a each turn. B reads one word each turn. Choose which word B reads and where the two words sit, then step or play.

One move costs

    Model, not a measurement. Each turn a core fetches each line it touches once: owned if it writes any word in it, shared if it only reads. A move is either a transfer (the line's bytes cross to the other core) or an invalidation (the writer tells the other core to drop its copy). Every move is charged the chosen one-way latency. The first load of each line comes from memory and is not counted. A real core can hide part of a write's invalidation behind other work; a read of a line the other core just wrote cannot be hidden, the core waits.

    False sharing and true sharing

    False sharing is unrelated data that happens to sit in one line: core B never needs a, yet A's writes still drag the line away from B and B's reads drag it back. Set B to read its own word and move the words to different lines: the moves stop. After each line's first load from memory, every access is a hit. Padding (putting unused bytes between the two words) fixes false sharing. True sharing is data both cores must touch because the protocol says so: B reads what A wrote. Now placement changes nothing; every round still costs a move each way, because the value itself has to travel. Padding cannot remove a transfer the protocol requires.

    The ring in this explainer has two such values, its two cursors. The producer writes its cursor to publish records, and the consumer must read it to find them. The consumer writes its cursor to free slots, and the producer must read it to find room. That is true sharing in both directions. Layout cannot make those moves go away. It decides only whether the two cursors travel together in one line or separately in two.

    One line or two: it depends on the access pattern

    Same simulator, now with the two cursors. The producer (A) writes cursor P every turn. The consumer (B) writes cursor C every turn. Each side also reads the other's cursor, either every turn or every fourth turn. The fourth-turn pattern stands for a side that keeps a private copy of the other cursor and re-reads the shared one only now and then. In one line, P sits at byte 0 and C at byte 64; in two lines, C moves to byte 128.

      Play both patterns in both placements and compare moves per round. With strict ping-pong, one line costs 2 moves a round and two lines cost 4: in one line, the single transfer that brings A the consumer's new C carries the line A is about to write P into, so one move does two jobs. With independent access, one line still costs 2 a round, because each side's own write steals the line from the other even when nobody needs the new value. Two lines cost 1 on average: each side writes its own line undisturbed, and moves happen only on the occasional read. So “put the cursors on separate lines” is the right default only when the two sides do not read each other every turn.

      Before the consumer cached the producer's cursor (pull request #41), the consumer read it on every pop. With 64 slots and one record per pop, the ring ran 87 to 98 M records/s with both cursors in one line and 22 to 27 M records/s with them in two lines.

      Stated confidence about 60%. “Natural batching” is the proposed reason one line won. When the consumer stores its own cursor it takes ownership of the whole shared line. The producer's next publishes wait in its store buffer (a queue of stores not yet visible to other cores) until the line comes back, then land together. The consumer then finds several new records per fetch and pops them as local hits. The measurements confirm the trigger: placement decides the speed, and caching the producer cursor in the consumer removes that dependence. They do not prove this mechanism. This machine had no hardware performance counters, so nobody counted the moves.

      What to carry into the next sections

      • A line is 128 bytes on this machine. Anything within the same 128-byte block moves as one.
      • One cross-core move costs about 37.8 ns (median, same cluster; 58 to 105 ns across clusters). At that price one line can cross at most about 26 million times a second.
      • A queue that pays one unhidden move per record is capped near 20 to 25 M records/s. Section 4 fits 40 to 48 ns per cursor re-read, and the slow layouts above sit at 22 to 27 M records/s.
      • The cursors are true sharing. Padding only chooses whether they travel together or apart; which is better depends on how often each side reads the other.
