Готові черги проти вимог споживача

Вимоги exchange_: тотальний порядок, lock-free (без блокування) шлях запису, явна політика переповнення, shutdown з зливом.

Жодне готове рішення не дає всіх вимог одночасно; частини залишаються еталонами й бекендами.

Чесність

  • rtrb лідирує на строгій парі одиночних записів: 3.4–3.6 нс проти наших 13–16 нс.
  • ArrayQueue лідирує на непакетному MPSC-шляху при високих кількостях продюсерів.
  • Але: потрібне поєднання — пакетування, стейджинг, політики, зупинка — і ніде цього набору немає.

crossbeam-queue — свідомий тимчасовий бекенд у ring_core за фіче-флагом.

Мʼютексова черга під навантаженням — це джитер у грошах: очікування на лок-і серіалізує потоки.

виміряно, не аргументовано

SPSC проти rtrb

ring_spsc проти rtrb — еталона однопродюсерного випадку. Порівняти можна лише всередині одного запуску.

Пропускна здатність двох потоків, M/с

Raspberry Pi 5 · 16 384 слоти · медіани criterion

Як читати чесно

  • Виграємо: 334 проти 244 млн записів/с (+37%) на 16 384 слотах.
  • Нічия: на 1024 слотах і 8-байтових записах різниця +1–2% — у межах шуму.
  • Програємо: rtrb лідирує на одиночних записах (3.4–3.6 нс проти 13–16 нс).
  • Лінія, не машина: абсолютні числа не переносяться; важлива лише різниця в одному рядку.

exchange_ взяв ring_spsc саме через виміряну перевагу на робочих місткостях.

програвання

Заповнення кільця заявками

Місткість 8. Потік-виробник кладе заявки один за одним; девʼята отримує відмову — потім злив відкриває шлях. Натисніть ▶ Пуск.

Rust · потік-виробник і exchange_step
use ring_factory::{ Factory, RingConfig };

let cfg = RingConfig::new( 8 ).unwrap(); // 8 slots, power of two
let mut split = Factory.build::< u32 >( cfg ).unwrap();
let ( mut producer, mut consumer ) = split.ends().split();

// потік-виробник: заявка №v прилітає по мережі
producer.try_push( v )                    // claim + publish
  .expect( "кільце повне — спробуємо знову" );

// exchange_step — один записувач
while let Some( order ) = consumer.try_recv() // злив у порядку claim-ів
{ /* перевірка → ескроу → зведення */ }

протокол

Claim / publish / commit

Slot-shaped channel з відтворюваним тотальним порядком і доставкою «лише один раз».

крок 1Claim

Продюсер резервує наступний номер послідовності — локально, без очікування.

крок 2Publish

пропуск ⇒ слот-привид
крок 3Available

Споживач бачить суцільний префікс номерів, готових до зливу.

тільки порядок claim-ів
крок 4Commit

Місце звільнено для повторного використання.

пропуск ⇒ вічне резервування

Що отримує споживач

  • Порядок: злиття в порядку claim-ів — тотальний, відтворюваний.
  • Exactly-once: кожен елемент ровно один раз.
  • Переповнення: промислова політика, а не сюрприз — Fail / DropNewest / DropOldest.
  • Зупинка: close → drain_all → reopen.

Не вигаданий патерн

Протокол відомий; його переписано й перевірено: loom перебирає переплетення, fuzz полює на паніки, гейти CI вміють падати.

Пропуск кроку ⇒ garbage / перезапис / вічне резервування — тому кожен крок несний без лок-а.

Ланцюжок

  • Споживач: exchange_ — багато потоків → один записувач → журнал і аудит.
  • Порівняння: жодна готова черга не дає всіх вимог; rtrb і ArrayQueue — еталони.
  • Виміряно: +37% проти rtrb на робочих місткостях; нічия — чесно названа.
  • Програвання: кільце заповнюється до відмови, зливається у порядку claim-ів.
  • Протокол: claim / publish / available / commit.
  • Далі: production-readiness — окремий план (capstone); exchange_ — реальний споживач, не продакшен-деплой.
