Why one store made a ring 4x slower, and how we found out

A lock-free single-producer, single-consumer ring got a cheaper slot type and, in one benchmark, ran four times slower. The slot was innocent. This is the chain of mechanisms behind that number: cache lines, two cursors, a layout decided by the length of an environment variable, a chase between two cores, and the one load that turned a faster producer into a slower queue. Every number here was measured on one Apple M4 Pro; every inference is labelled as one.

Pull requests: #41 the consumer caches the producer cursor · #38 CopySlot, stacked on #41.

01Cache lines

A core never fetches one byte from memory. It fetches a cache line: a fixed, aligned block of bytes that the caches store, copy and track as one unit. Touch one byte and the whole line comes along. The line is 64 bytes on x86 and most ARM cores. It is 128 bytes on Apple silicon, including the Apple M4 Pro where every number in this explainer was measured.

The unit the memory system moves

The ruler below is 256 bytes of memory, split into 8-byte words (one u64 each). Switch the line size and pick a word: the highlighted span is everything that moves with it.

Line size

One line, two cores

Each core keeps its own copy of a line in its L1 cache. A coherence protocol keeps the copies consistent with two rules. To write, a core must hold the only valid copy; every other copy is invalidated first. To read, a core needs a valid copy; several cores may hold the same line read-only, shared. When the up-to-date copy lives in the other core, the line has to cross over. On this machine one crossing between two performance cores in the same cluster took a median 37.8 ns (p25 37.3, p75 38.2). Across clusters it took 58 to 105 ns.

The simulator runs core A and core B in turns. A writes word a each turn. B reads one word each turn. Choose which word B reads and where the two words sit, then step or play.

One move costs

    Model, not a measurement. Each turn a core fetches each line it touches once: owned if it writes any word in it, shared if it only reads. A move is either a transfer (the line's bytes cross to the other core) or an invalidation (the writer tells the other core to drop its copy). Every move is charged the chosen one-way latency. The first load of each line comes from memory and is not counted. A real core can hide part of a write's invalidation behind other work; a read of a line the other core just wrote cannot be hidden, the core waits.

    False sharing and true sharing

    False sharing is unrelated data that happens to sit in one line: core B never needs a, yet A's writes still drag the line away from B and B's reads drag it back. Set B to read its own word and move the words to different lines: the moves stop. After each line's first load from memory, every access is a hit. Padding (putting unused bytes between the two words) fixes false sharing. True sharing is data both cores must touch because the protocol says so: B reads what A wrote. Now placement changes nothing; every round still costs a move each way, because the value itself has to travel. Padding cannot remove a transfer the protocol requires.

    The ring in this explainer has two such values, its two cursors. The producer writes its cursor to publish records, and the consumer must read it to find them. The consumer writes its cursor to free slots, and the producer must read it to find room. That is true sharing in both directions. Layout cannot make those moves go away. It decides only whether the two cursors travel together in one line or separately in two.

    One line or two: it depends on the access pattern

    Same simulator, now with the two cursors. The producer (A) writes cursor P every turn. The consumer (B) writes cursor C every turn. Each side also reads the other's cursor, either every turn or every fourth turn. The fourth-turn pattern stands for a side that keeps a private copy of the other cursor and re-reads the shared one only now and then. In one line, P sits at byte 0 and C at byte 64; in two lines, C moves to byte 128.

      Play both patterns in both placements and compare moves per round. With strict ping-pong, one line costs 2 moves a round and two lines cost 4: in one line, the single transfer that brings A the consumer's new C carries the line A is about to write P into, so one move does two jobs. With independent access, one line still costs 2 a round, because each side's own write steals the line from the other even when nobody needs the new value. Two lines cost 1 on average: each side writes its own line undisturbed, and moves happen only on the occasional read. So “put the cursors on separate lines” is the right default only when the two sides do not read each other every turn.

      Before the consumer cached the producer's cursor (pull request #41), the consumer read it on every pop. With 64 slots and one record per pop, the ring ran 87 to 98 M records/s with both cursors in one line and 22 to 27 M records/s with them in two lines.

      Stated confidence about 60%. “Natural batching” is the proposed reason one line won. When the consumer stores its own cursor it takes ownership of the whole shared line. The producer's next publishes wait in its store buffer (a queue of stores not yet visible to other cores) until the line comes back, then land together. The consumer then finds several new records per fetch and pops them as local hits. The measurements confirm the trigger: placement decides the speed, and caching the producer cursor in the consumer removes that dependence. They do not prove this mechanism. This machine had no hardware performance counters, so nobody counted the moves.

      What to carry into the next sections

      • A line is 128 bytes on this machine. Anything within the same 128-byte block moves as one.
      • One cross-core move costs about 37.8 ns (median, same cluster; 58 to 105 ns across clusters). At that price one line can cross at most about 26 million times a second.
      • A queue that pays one unhidden move per record is capped near 20 to 25 M records/s. Section 4 fits 40 to 48 ns per cursor re-read, and the slow layouts above sit at 22 to 27 M records/s.
      • The cursors are true sharing. Padding only chooses whether they travel together or apart; which is better depends on how often each side reads the other.

      02The ring and its cursors

      The ring under test is ring_spsc: one producer thread, one consumer thread, a fixed array of slots, and two counters. Every mechanism later in this explainer is a consequence of which of those two counters each operation reads and writes, so this section counts exactly that.

      Two cursors and an array

      The producer owns the producer cursor, produced: the sequence number of the next record it will write. The consumer owns the consumer cursor, consumed: the next record it will read. Both only grow. Record s lives in slot s mod capacity.

      Nothing else is shared. How many records wait is produced − consumed. The producer may write when that is below the capacity. No slot carries a full/empty flag, and no operation does a read-modify-write: each cursor has exactly one writer, so a plain store is enough to move it.

      Each end is a value one thread holds by &mut (exclusive access). An end may also keep private fields that no other thread can see. Those fields are where both caches below live.

      What one push and one pop do

      The disassembly of the fat-LTO bench binary agrees. Acquire compiles to ldapr, Release to stlr or stlur, and there is no dmb barrier anywhere between two pops. LDAPR is the RCpc form of load-acquire. Unlike LDAR, it may complete before an earlier STLR to a different address, so the consumer's commit store does not stall its next cursor load. The orderings cost almost nothing as instructions. What costs is the line the ldapr reads: the producer wrote it a moment ago, so its only up-to-date copy sits in the producer core's cache, and the load has to fetch it across cores (measured at ns one way, section 1).

      The per-pop cost is that coherence miss, not the Acquire ordering. Evidence: with the load weakened to Relaxed (a plain ldr), the slow cells stayed slow. Confidence high (orderings review, F1). No hardware performance counters were available to observe the miss directly.

      Release and Acquire, one record end to end

      The producer writes the payload 42 into slot 3, then publishes produced = 4. The consumer loads produced, sees 4, and reads slot 3. Release means every write before the store is visible to any thread that observes the stored value. Acquire means no read after the load can return data older than what the load observed. Together they form one edge: if the load sees 4, the read sees 42. Weaken either side and the edge is gone.

      Weakening is not a speed-up either: neither Relaxed variant removed the slow cells. On this machine both orderings are needed in practice, not only on paper.

      The consumer's cache (#41), and why == was wrong

      #41 gives the consumer what #20 gave the producer: one private field, cached_produced, holding its last GATING observation of the producer cursor. A drain reloads it only when the records it already knows of are fewer than the drain asks for:

    let produced = self.ring.cursors.producer().load(GATING);

      self.cached_produced = produced;

  }
  self.cached_produced

      drain() asks for usize::MAX, so it always reloads. drain_up_to(1) reloads only when it knows of nothing. When the producer is ahead, one load now serves many pops: in the ring above, with the cache on, Push ×4 then Pop ×4 loads the producer's line once instead of four times. The field is written only when the observation moved, so a consumer polling an empty ring does not store the same value every poll.

      The cache is sound for the same reason as the producer's: it can only lag. Every record it offers was published before a Release store that some GATING load by this end observed, on this drain or an earlier one, and program order carries that edge forward to the slot read.

      With the consumer cache, push1_pop1 at 64 slots with the cursors on two lines went from M records/s on master to (two rounds each). The results section has every cell.

      What loom checks here, and what it cannot

      Loom runs a small concurrent program under every interleaving it can generate and every outcome its memory model allows. The model a_bounded_drain_hands_out_only_records_whose_writes_it_can_see has a producer write a payload and push, twice, into a two-slot ring, while the consumer calls drain_up_to(1) twice and asserts each record's payload write is visible. It fails under a Relaxed reload and under a cache that extrapolates past its observation; before it, no loom model called drain_up_to at all. What loom cannot see is a cache that never reloads: that consumer hands out nothing wrong, it just stops, and a bounded model has no notion of "never". That mutant was caught by std tests, and the 100k-record threaded test hangs on it.

      03Where the ring lands

      The two cursors from the previous section live in one struct, Ring. Where that struct sits in memory moved the benchmark more than any change to the code did. This section follows the bytes: the struct, the stack that placed it, the benchmark framework that moved it between samples, and the slot array laid over the same lines.

      A 256-byte struct padded for 64-byte lines

      ring_align fixes the line size the whole ring family pads to (ring_align/src/lib.rs):

      pub const CACHE_LINE: usize = 64;

#[repr(align(64))]
pub struct CacheAligned<T>(T);

      Each cursor is padded to 64 bytes, and Ring is aligned to 64. Its four fields start 64 bytes apart: producer cursor at +0, consumer cursor at +64, capacity at +128, slot-array pointer at +192. That is 256 bytes in total. On x86-64 each cursor gets a line of its own. The M4 Pro's lines are 128 bytes, so two 64-byte fields share one line, and which two depends on the struct's address modulo 128. Alignment 64 leaves two possible answers.

      Field blocks run from each field's offset to the next one, padding included. Lines are drawn at 128 bytes, the M4 Pro's size.

      At 0 mod 128 both cursors share a line. Every store by either side takes the one line holding both, and the other core's copy is invalidated. At 64 mod 128 they sit on separate lines, which is what the padding was written to achieve. It measured slower: the closed PR #23, which padded the cursors to 128 bytes, was 3–7x slower on pop1 without #41. Section 4 explains why.

      In the two-line layout capacity (+128) lands on the consumer cursor's line, and the producer loads it on every push. Hoisting it into the producer removed the load from the assembly and left two-line pop1 as slow as before. It breaks the rule that no hot field shares a cursor's line. It is not the regression.

      The harness never chose the address

      The benchmark built the ring as a temporary on the main thread's stack. On macOS the stack pointer at main sits just below the argv and environment strings, so anything that lengthens them pushes the stack down. The ring is aligned to 64, so a 16-byte move shifts it by 0 or 64 bytes. When it shifts, 0 mod 128 becomes 64 mod 128 and one line becomes two.

      The test that settles it: run the unmodified PR #38 binary with one unused environment variable, PAD, of 1 to 113 characters. Push one, pop one, criterion medians.

      The check that never read the middle line

      The 256-byte row put TypedSlot at a 264-byte stride against CopySlot at 256. The consumer checks each record with Wide::whole (perf/benches/harness/candidates.rs), and the check compared two words:

      At a 264-byte stride each record spans three lines.       04Who chases whom

      Section 3 showed the same code running at about 24 M/s or about 200 M/s depending on where the two cursors landed. This section explains the slow number. No single load got slower. The two threads settled into a state where every record costs one cross-core round trip.

      The chase

      Two threads on two cores. The producer spends p ns of its own work per record; the consumer spends c ns. Neither waits for the other until the ring forces it to.

      • If the producer is faster (p < c), it gains a little on every record and the ring fills. Now the producer is the one that keeps hitting a wall: its cached copy of the consumer cursor says full, and it has to read the consumer's cursor line to find out whether a slot was freed.
      • If the consumer is faster (c < p), the ring runs nearly empty. The producer's cache says room for almost a whole lap, so it reads the consumer cursor about once per lap. The consumer is the one waiting, on the producer cursor.

      So where the ring sits decides which cross-core reads happen and how often. Here is the producer's side, from claim in ring_spsc/src/lib.rs (the producer cache from #20):

      if self.cached_head.distance_to(self.cached_tail) >= capacity {
  // The cache says full. [...] refresh the observation once
  self.cached_head = self.ring.cursors.consumer().load(GATING);

      Call that load a refresh. It is the only time the producer reads the consumer's cursor line. When the refresh finds R free slots, the producer pushes R records before it needs the next one.

      The full-ring lockstep

      Take the case that went wrong: the consumer is a little slower, the ring is full, and the benchmark pops one record per call (push1_pop1). Step through it.

      The consumer frees one slot and commits. The producer's cache says full, so it refreshes: one cross-core round trip. It finds exactly one free slot, pushes once, and is full again. Each refresh buys one push. The ring is never short of records; the consumer is slow because each slot it frees is fought over at once.

      Slow push1_pop1 runs refresh 0.5 to 1.0 times per record, and the refreshes find room for exactly one slot. Fast runs refresh at most 0.04 times per record. The review counted the refreshes with a counter added to Producer; no hardware counters were available on this machine.

      The model

      A refresh finds room R. The producer spends R·p pushing, then m on the next refresh. In that time the consumer frees one slot every ceff ns, so the next refresh finds R′ = (R·p + m) / ceff.

      • Cache on: ceff = c. If c > p, R settles at R* ≈ m / (c − p). The ring parks near full, but each refresh still buys R* pushes.
      • Cache off: ceff = c + r + m/R. The r is the consumer reading the producer's cursor line on every pop. The m/R is the feedback: each refresh takes the consumer's cursor line away, and the consumer pays to take it back. Substitute and R′ − R has the sign of p − (c + r). There is no stable middle: a consumer slower by any amount drives R to 1.

      With the cache off, time per record is c + r + m × refreshes/record, the same shape as the fit above: the intercept is the consumer's own work, the slope is one refresh.

      The feedback term, a refresh costing the consumer a line re-acquisition when the cursors sit on separate lines, was inferred from how added delays moved the result. Nobody observed it: there are no PMU counters on this machine. Review "regimes" rates the direction high confidence and the thresholds medium. The model keeps three costs and nothing else. It gets the direction of all three measured interventions right and over-predicts the gain from slowing the producer.

      Why CopySlot tipped it

      CopySlot (#38) dropped the tag store from the producer's push. The consumer's pop did not get cheaper. That shrank p and left c alone, and on the two-line layout it was enough to flip the sign of c − p: the producer became the faster side, the ring filled, and push1_pop1 fell into lockstep.

      Slowing the producer by 3–9 ns per push on two lines took the ring from 22–28 M/s to 54–68 (TypedSlot) and 34–53 (CopySlot): a slower producer made the ring 2 to 2.5 times faster. The refresh rate fell with it.

      Anomaly A, and the binary that hid the edge

      One cell refused the story: TypedSlot at 1024 slots stayed fast with its cursors on two lines (196 and 232 M/s) while CopySlot crawled (24 and 36). The cause was not the slot. LLVM inlined the TypedSlot adapter's pop_batch into the benchmark's consumer loop and left the CopySlot one as a call. That shaved the consumer just enough to keep c below p.

      With TypedSlot fast on two lines (267 M/s), slowing the consumer by about 1 ns per record dropped it to 19.9–23.6 M/s, back into lockstep. On one line the flip took a consumer slowed by 4.5–6 ns (76–110 M/s down to 19–33).

      This is a knife-edge. On two lines the cell sits where c ≈ p, and which side of the edge it lands on depends on a nanosecond of code generation in the consumer loop. Any two-line push1_pop1 number from before the consumer cache measures the compiler's inlining choice as much as the ring.

      Inlining as the cause of anomaly A: review "uarch" rates it about 95%. The exact trigger, inlining or loop unswitching, was not isolated.

      What the consumer cache changes, and what it does not

      The consumer cache (#41) makes the consumer read the producer cursor only when it has run out of records it already knows about. On a full ring that is once per batch of known records, not once per pop. That removes r and the per-pop line traffic the feedback rides on, so the two layouts agree and the edge moves far out: in the model, lockstep now needs c − p ≥ m.

      push1_pop1, M/s, two roundsTypedSlot, masterTypedSlot, #41CopySlot, no cacheCopySlot on #41

      It does not remove the state. With an artificial delay making the consumer slower, the cached ring still parks at full and the refresh rate climbs again (measured by review "regimes"). A ring whose consumer is slower than its producer will sit full; the cache only makes sitting full cheaper. What removes the state is draining more than one record per pop: push1_popN drains a whole lap per call, and one refresh then buys a lap.

      The opposite race: popN

      In push1_popN a full ring is the good state: the consumer takes a whole lap per call and the producer refreshes once per lap. The 1024-slot cell is bimodal on every stage (for example 416 and 272 M/s for #41 on one line) because the initial race picks, per run, whether the producer gets ahead or the consumer catches it and drains tiny batches, and either state sustains itself.

        Open questions

        1. Why is a 64-byte stride slow at the frontier? Ruled out: 4K aliasing, more line sharing, codegen. Padding to 72 bytes fixes it; the mechanism needs hardware counters.
        2. Why did #41 slow two single-thread benchmarks? push_pop (3.60, 3.73 → 3.98, 3.98 ns) and whole-lap fill_drain at 64 and 1024 slots. Labelled code layout; not observed directly.
        3. What holds TypedSlot at 16384 slots to 25–48 M/s in every mode and layout? Likely the 256 KB slot array spilling the 128 KB L1D (CopySlot's is exactly 128 KB). The regimes review rates the label medium and the cause low. #41 takes pop1 there from 46, 47 to 36, 35.
        4. Which mode of the bimodal popN 1024 cell is typical? The regimes review attributes the two modes to the chase's initial race (high confidence). A separate review tied the tagged flip to the slot array sitting one page after the ring, mechanism unknown.
        5. Where does the lockstep threshold sit now? The cache moved it. The steady-state model R* ≈ m / (c − p) (m one refresh ≈ 45 ns, c the consumer's cost per pop, p the producer's cost per push) was fitted qualitatively; c and p were never measured in isolation.
        6. Does the one-line layout batch about 4 records per transfer? Consistent with the timings (one-way 37.8 ns against ~9–10 ns per record), unobservable without counters. Hypothesis, ~70% confidence.
        7. Should CACHE_LINE become 128? With #41 the two layouts measure the same on pop1, so this is now a footprint decision, not a speed one.

        Glossary

        Cache line
        The unit a cache stores, moves and keeps coherent. 128 bytes on this M4 Pro; ring_align assumes 64.
        Coherence transfer
        Moving a line, or its write ownership, from one core's cache to another's, invalidating the old copy. One way inside a P-core cluster: median 37.8 ns.
        Stride
        Bytes from the start of one slot to the start of the next: 16 for TypedSlot<u64>, 8 for CopySlot<u64>, 72 against 64 and 264 against 256 for the wide records.
        Frontier
        The slots the producer is writing while the consumer reads right behind it. Lines there are hot on both cores at once.
        Lockstep
        The full ring with the producer one slot behind the consumer: it refreshes its cached consumer cursor before nearly every push, about 48 ns each.
        OWN, GATING, HANDOFF
        The three orderings the ring uses. OWN is Relaxed: an end reading the cursor only it writes. GATING is Acquire: reading the other end's cursor before touching the slots it guards. HANDOFF is Release: publishing one's own cursor after the slot writes.
        LDAPR, STLR
        The AArch64 instructions behind them: LDAPR (and LDAPUR) an acquire load in the weaker RCpc form, STLR (and STLUR) a release store. A push does one STLR; before #41, every pop did one LDAPR.
        loom
        A Rust model checker. It runs a concurrent test under every interleaving the memory model permits, up to a bound, and so catches orderings a real run rarely exposes.
