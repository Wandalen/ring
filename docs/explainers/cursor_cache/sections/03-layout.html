Where the ring lands

The two cursors from the previous section live in one struct, Ring. Where that struct sits in memory moved the benchmark more than any change to the code did. This section follows the bytes: the struct, the stack that placed it, the benchmark framework that moved it between samples, and the slot array laid over the same lines.

A 256-byte struct padded for 64-byte lines

ring_align fixes the line size the whole ring family pads to (ring_align/src/lib.rs):

pub const CACHE_LINE: usize = 64;

#[repr(align(64))]
pub struct CacheAligned<T>(T);

Each cursor is padded to 64 bytes, and Ring is aligned to 64. Its four fields start 64 bytes apart: producer cursor at +0, consumer cursor at +64, capacity at +128, slot-array pointer at +192. That is 256 bytes in total. On x86-64 each cursor gets a line of its own. The M4 Pro's lines are 128 bytes, so two 64-byte fields share one line, and which two depends on the struct's address modulo 128. Alignment 64 leaves two possible answers.

Field blocks run from each field's offset to the next one, padding included. Lines are drawn at 128 bytes, the M4 Pro's size.

At 0 mod 128 both cursors share a line. Every store by either side takes the one line holding both, and the other core's copy is invalidated. At 64 mod 128 they sit on separate lines, which is what the padding was written to achieve. It measured slower: the closed PR #23, which padded the cursors to 128 bytes, was 3–7x slower on pop1 without #41. Section 4 explains why.

In the two-line layout capacity (+128) lands on the consumer cursor's line, and the producer loads it on every push. Hoisting it into the producer removed the load from the assembly and left two-line pop1 as slow as before. It breaks the rule that no hot field shares a cursor's line. It is not the regression.

The harness never chose the address

The benchmark built the ring as a temporary on the main thread's stack. On macOS the stack pointer at main sits just below the argv and environment strings, so anything that lengthens them pushes the stack down. The ring is aligned to 64, so a 16-byte move shifts it by 0 or 64 bytes. When it shifts, 0 mod 128 becomes 64 mod 128 and one line becomes two.

The test that settles it: run the unmodified PR #38 binary with one unused environment variable, PAD, of 1 to 113 characters. Push one, pop one, criterion medians.

Criterion moved it again, between samples

Criterion 0.8.2 wraps sample i in alloca(i % page_size), a de-biasing step meant for 100 samples. The harness ran 10. The shim is a variable-length array, so sizes 1–9 round up to 16 bytes: sample 0 runs at shift 0, samples 1–9 at shift 16. When the stack sits where 16 bytes crosses a 64-byte boundary, sample 0 gets one layout and the other nine get the other. Warm-up has no alloca and a different call depth, so it is a third placement. That explains the bimodal cells and the "low severe outlier" criterion kept reporting.

Offsets 0 and 128 give the same layout, and so do 64 and 192. The bars agree in those pairs, which a layout effect predicts and a slot effect does not.

With #[inline(always)] on both adapters, every slot shape measured 24–37 M/s on two lines and 100–112 on one line.

The two fast TypedSlot cells at 1024 slots on two lines (196 and 232) are a compile artefact: LLVM inlined the tagged adapter's pop_batch and outlined the plain one. The inlining difference was read from the binaries' symbol tables, not from counters. The inline(always) rerun above is what makes the artefact reading the likely one.

Slot strides decide what shares a line

The slot array is the other thing laid over these lines. TypedSlot<T> wraps an Option<T>, whose tag costs 8 bytes per slot at these sizes. CopySlot<T> has no tag. The stride is the distance from one slot's start to the next.

The slot array starts on a line boundary. For TypedSlot the tag is drawn at the slot's start; rustc chooses the order.

64-byte records, two rounds each, M/s: CopySlot at stride 64 ran 38 / 53; the same CopySlot padded to 72 ran 81 / 96. TypedSlot at 72 ran 70 / 85; TypedSlot with the tag removed (stride 64) ran 52 / 73. The stride decides, not the slot type. With the consumer held 64 records behind the producer the stride stops mattering: 180 vs 177 at 64 vs 72, 110 vs 113 at 256 vs 264. Single-threaded fill-then-drain shows the opposite: stride 64 ran 707 against 483 at 72. Stride 128 runs within ~10% of 136.

The 64-byte-stride penalty lives at the frontier, where the producer writes slot i+1 next to the slot i the consumer reads; it vanishes when the two are 64 records apart. Why a power-of-two stride is slow there is not known. This machine exposed no PMU counters. Ruled out: 4K aliasing (a same-core effect that would not vanish with lag), more line sharing (72 shares more boundaries yet is faster), and codegen (both store inline, no memcpy).

The check that never read the middle line

The 256-byte row put TypedSlot at a 264-byte stride against CopySlot at 256. The consumer checks each record with Wide::whole (perf/benches/harness/candidates.rs), and the check compared two words:

-    self.0[0] == self.0[N - 1]
+    self.0.iter().all(|word| *word == self.0[0])
word the check readstagline no read touches

At a 264-byte stride each record spans three lines. The first word shares a line with the previous record's tail, the last word shares one with the next record's tag, and the middle line is never touched, so it never crosses cores. At 256 the first and last words sit on two different lines that no other record touches. The benchmark measured the checker's footprint, not the queue's.

The fix reads every word. Push one, pop many, 1024 slots, two rounds, M/s: TypedSlot fell from 46.9 / 52.0 to 31.8 / 30.2. CopySlot went from 26.6 / 26.9 to 29.4 / 29.1, and rtrb reads 31.0 / 29.6. The 256-byte gap was the check. The 64-byte gap survives the fix: TypedSlot 99.3 / 93.7 against CopySlot 62.6 / 44.6. That one is the stride effect above.
