# Decision: Should `PARKING_CRATES` Be Generated Rather Than Written

**Status:** open, pending `ring_bench` giving the family a reason to have a
build-time metadata step at all.

### Scope

- **Purpose**: Record the open question of whether the parking roster should be computed from `cargo metadata` instead of typed by hand, and the threshold that would settle it.
- **Responsibility**: What is actually at stake (not correctness), the three arguments against the current form, the measurement that would decide, and why it is filed rather than decided.
- **In Scope**: The roster's form; the tripwire property; the size threshold.
- **Out of Scope**: Whether the roster should exist at all (→ [`../pattern/001`](../pattern/001_enforcement_by_dependency_graph.md), part 2); the claim it serves (→ [`../invariant/001`](../invariant/001_no_parking_operation_on_the_tick_path.md)).

### The Question

`ring_poll::PARKING_CRATES` is three string literals typed by hand. The set they
name is derivable — it is exactly the crates whose manifests mention `ring_wait`
— and `cargo metadata` can compute it. So: should the constant be generated by a
build script instead of written down?

### What Is Actually at Stake

Not correctness. The test already compares the constant against the manifests,
so a stale roster fails the suite; that is the property
[`../pattern/001`](../pattern/001_enforcement_by_dependency_graph.md) says is
load-bearing, and it holds either way.

What is at stake is *which direction the failure points*.

| Roster form | A crate gains `ring_wait` | The failure says |
|---|---|---|
| **Hand-written** (today) | Test fails | "The graph changed. Decide whether that was intended, then edit the public constant" |
| **Generated** | Test passes | Nothing. The constant regenerates to match |

Generation makes the constant always-correct and therefore says nothing. The
hand-written version is a *tripwire*: its whole value is that it goes wrong when
the graph moves, which is the moment a human should look.

### Why It Is Not Simply Settled, Then

Three arguments on the other side, and none is negligible:

1. **The same reasoning would reject every generated manifest fact**, and the
   family already generates plenty without regret.
2. **A hand-maintained roster is the family's known weak spot.** `ring_types`'
   variant list has the same shape and is recorded as a deferred blocker for
   exactly this reason. Two instances of a pattern that is wrong is worse than
   one.
3. **The tripwire only works if the failure is legible.** Today it is —
   `assert_eq!` prints both sets. If the roster grew to a dozen entries the diff
   would stop being readable, and the tripwire would become an obstacle rather
   than a signal.

Argument 3 is the one with a threshold in it, which makes it the useful one: the
hand-written form is right *while the roster is small*, and the decision is
really about where small ends.

### The Measurement That Would Settle It

Roster size, and how often it changes:

### Regenerate

```sh
cd "$(git rev-parse --show-toplevel)"
printf 'roster size, manifest scan:  %s\n' "$( for c in ring_*/Cargo.toml; do command grep -q 'ring_wait' "$c" && echo x; done | wc -l )"
printf 'roster size, normal closure: %s\n' "$( for c in ring_*/; do n=$( basename "$c" ); cargo tree --manifest-path Cargo.toml -e normal -p "$n" 2>/dev/null | command grep -q 'ring_wait' && echo x; done | wc -l )"
printf 'the threshold proposed here: %s\n' "$( command grep -oE 'at [0-9]+ or more, generate it' ring_poll/docs/decisions/001_should_the_roster_be_generated.md | command grep -oE '[0-9]+' )"
printf 'build scripts in the family: %s\n' "$( ls ring_*/build.rs 2>/dev/null | wc -l )"
printf 'cargo-metadata call sites:   %s\n' "$( command grep -rl 'cargo_metadata\|cargo metadata' ring_*/src ring_*/tests 2>/dev/null | wc -l )"
printf 'the owner named here:        %s\n' "$( command grep -oE 'ring_[a-z]+. owns it because' ring_poll/docs/decisions/001_should_the_roster_be_generated.md | command grep -oE 'ring_[a-z]+' )"

Live output:

```

the threshold proposed here: 6

the owner named here:        ring_bench

**Proposed threshold: at 6 or more, generate it and move the tripwire to a gate**
— a gate can diff a generated set against a *declared intent* file and report the
difference, which keeps the human moment without keeping the hand-typed list.
Below 6, the hand-written constant costs three lines and buys a stop sign. Which
count sits below 6 is ambiguous: the manifest scan reads 3, comfortably clear;
the *reachable* count — the reading the roster's own doc comment claims to name
— reads 5, one crate away from the line rather than three.

### Why This Is Filed Rather Than Decided

The threshold above is a guess, and the evidence that would justify it — how
often the family's dependency graph actually changes — does not exist yet because
the family is three weeks old and half-built. Filing it with the measurement
attached is honest; picking 6 now and writing it into a rulebook would be
inventing a certainty.

`ring_bench` owns it because it is the first thing that will need build-time
metadata for its own reasons, and this decision is cheap to fold into that work
and expensive to do on its own.

### PL13 — the threshold is set against a count the decision never takes

The settling measurement written into this document counts the crates whose
manifests mention `ring_wait`. That is three, and the proposed threshold is six,
so the decision reads as comfortably settled for now — half way to the line.

There is a second count. The crates from which `ring_wait` is *reachable*
through normal dependencies are five: `ring_consume` arrives via `ring_barrier`
and `ring_testkit` via `ring_shutdown`
([`../api/002`](../api/002_the_roster_as_a_public_constant.md) PL7). One below
the threshold, not three.

Which count is the right one is exactly the question the roster's own doc
comment gets wrong — it says *reachable* and lists declarers. So this decision
inherits the ambiguity rather than resolving it, and inherits it in the place
where it matters most: the number that decides whether to act. Under the
reachability reading the family is one crate away from the point at which this
document says to stop hand-writing the list.

The threshold itself was flagged as a guess when it was written, and that is
still fair. What the guess is measured against is not a guess, and it is the half
that can be corrected without new evidence → [`002`](002_reach_or_declaration.md).

```sh
cd "$(git rev-parse --show-toplevel)"
command grep -m1 -F "one crate away from the line rather than three" ring_poll/docs/decisions/001_should_the_roster_be_generated.md
```

Live output:

```
— reads 5, one crate away from the line rather than three.
```

**Disposition:** applied — the Proposed threshold paragraph now names both
counts explicitly and states which is closer to the line: the manifest scan
(3) reads comfortably clear, but the reachability count (5) — the reading the
roster's own doc comment claims to use — is one crate away from 6, not three.
Now prints: `one crate away from the line rather than three`

### PL14 — the option this decision defers to has no precedent in the family, and the trigger it was pinned to hasn't fired

"Generate it from `cargo metadata`" is one of two options here, and the document
defers the choice on the grounds that *"`ring_bench` is the first thing
that will need build-time metadata for its own reasons, and this decision is
cheap to fold into that work."*

`ring_bench` now exists and is 1098 source lines — the second largest crate in
the family, behind `ring_mpsc`. It has no build script. Neither does any other `ring_*` crate — the family has zero `build.rs`
files and zero call sites naming `cargo metadata` or the `cargo_metadata` crate,
in `src/` or in `tests/`.

So the cheap-to-fold-in premise has not come true, and the crate it was pinned to
has been written past it. That does not make the decision wrong; the tripwire
argument stands on its own and the hand-written roster still costs three lines.
What it makes wrong is the *deferral*: this question is not waiting on work
already scheduled, it is waiting on work nobody has scheduled, and the document
reads as though the former were true.

A deferred decision whose unblocking event has silently not happened is
indistinguishable, from the outside, from one that is still on track. Recording
the measurement is what makes the difference visible, and re-running the recipe
above is how a later reader learns which of the two states this is in.
